# Video best practices (this demo family)

Started 2026-11-21. Add to this as we learn more; these are the rules that cost us a take to learn.

## Standards, as of 2026-11-21

- **Light mode by default.** `THEME` defaults to `"light"` in `take.py`. Pass `THEME=dark` to override for a specific take.
- **Every video opens with a title slide** comparing the approach used to the obvious alternative (here: CIMD vs DCR) and stating which one this demo uses and why. Full-screen card, not a small caption bubble.
- **Every video closes with a summary slide**: what the run just showed, and why it matters. Same full-screen treatment as the opening slide.
- **Wording lives in `captions.md`, not in `take.py` or `captions.py`.** Edit the text under each heading there; don't touch `take.py` for a wording-only change. `captions.py` is just a loader that parses `captions.md` into the shape `take.py` expects, and fails with a clear message (naming the exact step) if a heading is renamed or a required section goes missing. `take.py` fills in the live data (a URL, a status code) around whatever prose is written in `captions.md`.
- **Write the script first, from the specs and docs (added 2026-11-21).** Every video has a `SCRIPT.md` written before any recording or caption: audience, the one idea, a **Sources** table (each spec, RFC or vendor doc actually read for it, with its version/release and URL), then a scene table (on screen / caption / source tag). Every factual claim in a caption traces to a source tag or to the demo's own README; a claim with no source is cut or marked "verify". The script also lists **checks before recording** (what must be true of the live system for the script to be true, e.g. the banner says LIVE, the auth setup is what scene N says) and **what is deliberately not in the video**. `captions.md` carries the on-screen wording and must say what the script says; if a source changes, change the script, then the captions, then retake. Where the spec and the product's wire format differ (a newer spec release than the vendor ships), say so on the opening slide rather than hiding it.
- **Build and review a SAMPLE before the real take (added 2026-11-21).** Every video gets a sample first: `SAMPLE=1` runs the same `take.py` against the mock/stand-in, headless at full timing, and writes `sample.mp4`. The sample labels itself (a SAMPLE pill, plus sample-only wording in `captions.md` so it never claims to be a live run), the person reviews it, wording and pacing are fixed, and only then is the real take recorded. A sample is never handed over without its contact sheet checked. Three modes of `take.py`: `REHEARSE=1` (headless, fast, no video, for selectors and timing), `SAMPLE=1` (the preview), default (the real take, ffmpeg screen capture). Fixed on the first sample: counter says "N of TOTAL" with TOTAL matching the real step count; a caption fact line is the first full sentence of the live text, never cut mid-word; the mode pill goes bottom-right so it never covers the app's own title.
- **Verify the script's facts with an independent second reader (added 2026-11-21).** After the script's sources are read, have a second reader re-fetch every cited source and try to refute each fact (wrong section number, MUST/SHOULD inflated, a claim the page never makes, true only of an older release). Keep the corrections, and keep the researcher's "gaps" (things looked for and not found) as the list of things the video must not claim. On the AWS A2A video this caught, among others: the 1.0.0 spec never uses the name `message/send`; section 7.3 has no MUST/SHOULD; RFC 7235 (cited by AWS) is obsoleted by RFC 9110; Ping documents no status code for a denied agent request, so the live run, not the docs, supplies the 401.
- **Review the draft before the sample, with independent lenses (added 2026-11-21).** Spec/doc accuracy; truth against what was actually observed on the live system (a statement the run did not prove is an overclaim, even if the docs say it); audience and pacing (undefined jargon, words per slide); a code review of any app change made for the video; and a sensitive-data scan (account ids, hostnames, tokens, on screen and in the repo). Each finding is re-checked by a skeptic before it is acted on. This is what found that a caption said the refusal demonstrated a policy check when it demonstrated an authentication failure, that the old take showed an AWS account id, and that a "reachable only through the gateway" claim had no source.
- **Show enforcement both ways (added 2026-11-21).** A video about a policy point shows a success and a refusal, from the live system. The refusal is a real refusal (a deliberately invalid credential, which is not a secret), the take checks it really was refused where the script says, and the closing slide only claims what the live response actually carried (for example, a `resource_metadata` pointer in the challenge).
- **Show the real configuration, read-only (added 2026-11-21).** When a video explains how a product is set up, read the real console (read-only: pages and text, never a click that changes state), say on the slide when it was read, and keep the screenshot local (`assets/` is gitignored when the repo is public and forbids internal hostnames). If the console session expires mid-read, stop: never sign in on the owner's behalf.
- **No slide is held longer than 10 seconds (owner, 2026-11-22; replaces the four-words-a-second rule).** Write each slide to be skimmed in 10 seconds: about 75 words at most, short bullets, the opening slide shortest. Detail belongs in the captions and pop-outs, or in the deck. Put a reference slide just before the closing, not before the first call. Define a term the first time it appears.
- **Two videos, one per screen, each exactly the screen's size (owner, 2026-11-22; replaces "record on the middle-size screen").** Every video is recorded twice from the same script: a **monitor** cut for the middle 1920x1080 external monitor (`PROFILE=monitor` in `take.py`: app text size L, slides and captions scaled up about 1.3x, 1920x1080) and a **laptop** cut for the built-in display (`PROFILE=laptop`: app text size S so busy screens fit, slides and captions at normal size, rendered at 2x and recorded at 2400x1558; scroll where something still does not fit). File names: `<name>-monitor.mp4` and `<name>-laptop.mp4`. **Record straight from the browser at exactly that size (`HEADLESS_REAL=1`, the live run, Real mode), not by capturing the screen.** Screen capture of a full-screen window lost two takes in one session: another session's browser and a macOS permission prompt covered the monitor, a system "Server connections interrupted" dialog landed on the laptop, and the full-screen Space switched away mid-take so the video showed the desktop wallpaper. The headless route is immune to all of that, needs no quiet Mac, and the two cuts can record at the same time. Screen capture (`PROFILE=... python3 take.py`, Chrome `--kiosk`, `MONITOR=medium|laptop`) stays available when a real-screen recording is wanted; then leave the Mac alone, read the display layout first (`NSScreen` frames; Quartz y = main height - (y + h)), and look at every frame of the contact sheet before calling the take good. Include the Privilege console screenshots (read-only, kept local) for any video about Privilege configuration.
- **Every video ends with an observability slide (owner, 2026-11-22; also demo rule 27 in STANDALONE-RULES.md).** The slide goes right before the closing slide and shows what the recorded run left behind: the log or audit entries for what was allowed, and for what was refused or blocked, with their timestamps, read from the product's own logs (read-only, ids and tokens masked) and captured from the very run in the video, not an earlier one. Say where the logs live and where they can stream (a SIEM). Where an event is not logged, say so; never claim it. Build it by recording the main take to just before the end slides, capturing the logs straight after, then recording the end segment (protect, observability, closing) and joining the two with ffmpeg (`SEGMENT=main`, `SEGMENT=end`, `join.sh`). In the A2A lab pipeline: the main take saves the lab's own `GET /api/run-observability` record after every run (into result.json); `build_obs_slide.py <main-take-dir>` turns those records, plus the lab's own stdout decision lines read read-only with `docker logs` over the take's time window, into `assets/observability.json`; the end segment then draws the slide. Never mount the Docker socket into a lab to get log lines (the lab's own opt-in Docker reader is for an owner-run ad-hoc capture only); keep the slide to about three lines per column so it fits the screen, and cut text at a word.
- **Check for other recordings first, and never kill Chrome for Testing by name (2026-11-22).** Several sessions record videos on this Mac, and two of them were fighting: one session's browser covered the other's recording, and a cleanup of "Chrome for Testing" or "take.py" by one killed the other's take (a take that dies before it closes its recording leaves a webm with no ending). Before a take run `ps aux | grep -E "take.py|ffmpeg.*avfoundation"` and wait for anyone else's; kill only your own pids; run your take under a name nobody else uses (`a2a_video_take.py`); and treat a recording shorter than the take's own timeline as lost.
- **Use the real spec, don't just gesture at the idea.** When a video demonstrates something a published spec or RFC actually defines, look the spec up (don't rely on memory alone — specs get revised), name it precisely (the real draft/RFC number, not an informal label), and cite it on the opening and closing slides. Then, where it's a natural fit, tie a specific rule to the exact moment the demo shows it happening ("the spec requires X; here it is") — a handful of these through the body of the video, not one on every step. Never quote spec text verbatim at length; paraphrase the rule in the video's own voice.

- **First page title (owner, 2026-11-24; STANDALONE-RULES rule 29).** The first frame of every video is a page whose header says what is being shown (here: "A2A, and A2A with an AWS agent"). The same header is on the live Story's first page.

## Before every recording

1. **Re-verify the capture device after any monitor change.** A different number of displays, a different arrangement, or even macOS reassigning indices after a reconnect will silently break the capture (ffmpeg fails instantly with "Invalid device index", or — worse — succeeds while capturing the wrong screen or at the wrong scale). Don't assume last time's `CAPTURE_DEVICE`/`DISPLAY_X`/`DISPLAY_Y` still hold.
   - List current screens: `ffmpeg -f avfoundation -list_devices true -i ""`
   - Confirm which device is the window's actual screen, and at what scale, with a **green-marker calibration**: launch a throwaway Chrome window at the candidate position with a solid `#00FF00` page background, capture one frame from each candidate device, and scan for a large contiguous green run (not just "any green pixel" — desktop wallpapers have false positives). The ratio of the matched pixel width to the window's own `innerWidth` is the display's scale factor (1 for a standard display, 2 for Retina).
   - `take.py`'s crop math multiplies by `window.devicePixelRatio`, so it's correct once `CAPTURE_DEVICE`/`DISPLAY_X`/`DISPLAY_Y`/`WIN_X`/`WIN_Y` point at the right screen — it does not need a manual scale override.
2. **Rehearse headless first** (`REHEARSE=1`, against a local stand-in or the live app with `NOLOGIN=1`) before any take that needs a real sign-in. It catches selector breakage, missing frames, and caption timing for free, in under a minute.
3. **Restart the pod clean** right before recording, and re-set Real mode and the model afterward — a fresh run has zero hops and a signed-out state, which is what the video should open on.

## During recording

- **The Chrome profile has the password manager switched off** (`credentials_enable_service: false` etc., set in `take.py`'s throwaway profile) — no "Save password?" bubble should ever appear. If one does, the profile setup broke; fix that, don't just dismiss the bubble.
- **The overlay scrolls a target into view before highlighting it** (`cap()`'s `t.scrollIntoView(...)`). If a caption still points at the wrong place or off-screen content, that's a real bug, not something to work around by repositioning the window.
- **A caption's wording and the thing it points at should agree.** When the live app's own labels differ from the caption's own language (for example the app's reel frames may still say "door" while a caption says "AI Gateway" — a narration-only change doesn't touch server-side hop titles), say so in the handoff rather than letting it look like an oversight.

## After recording

- **Check the hops via `/api/state` before trusting a take**, especially for anything the demo is meant to prove (a fix, a permission, a refusal). The video can look clean and still have recorded a silent failure.
- **Pull a contact sheet** (`ffmpeg -vf "fps=1/N,scale=480:-1,tile=4x4"`) and look at it before handing a take over. Catches a wrong crop, a missing frame, or a caption that landed on top of something it shouldn't have, in one image instead of scrubbing the whole video.
